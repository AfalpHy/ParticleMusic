# USB 快速连续音量点击防抖设计

## 背景

真机日志显示，快速连续点击手机音量键时，点击间隔约为 170–210ms；单次 iBasso HID 写入和读回通常需要约 130–150ms。现有协调器虽然只允许一个运行中事务和一个待处理目标，并在相邻事务之间保留 150ms 间隔，但会在间隔结束后立即执行待处理目标。连续点击因此仍可形成持续 HID 事务，最终造成 reader 重启、再次读回失败和 PCM 硬件音量冻结。

失败前的 ReplayGain 保持不变，说明网络源不是直接原因；网络切歌和安全渐升只会增加事务密度。需要修复的是所有来源共用的 Android 音量事务调度，而不是单独照顾某个来源或设备型号。

## 目标行为

- 单次点击保持低延迟：协调器空闲时立即执行第一个绝对目标。
- 快速连续点击时，Flutter UI 每次点击立即更新；Android 待处理槽只保留最新绝对目标，不形成历史队列。
- 第一笔事务后的目标必须同时满足：
  - 距离上一事务完成至少 150ms；
  - 距离最后一次待处理输入至少 300ms。
- 安静窗口内收到新目标时重新计时，停止点击后只执行最终绝对目标。
- 切歌、停止或 session generation 变化后，旧目标不得作用于新会话。
- 保留现有 reader 恢复、旧可信目标、PCM 冻结、DSD 暂停和音量上升保护，不通过延长 HID ACK 超时掩盖问题。

## 方案比较

### 方案 A：Android 协调器首笔立即、尾部防抖（采用）

在现有单事务协调器中记录待处理目标最后更新时间。运行中事务完成后，循环计算剩余等待时间；等待期间若有新输入，则继续以最新时间和最新绝对目标为准。

优点是覆盖音量键、Slider、ReplayGain 和模式变化等全部来源，不增加新的队列或管理类。代价是连续操作期间 DAC 硬件值会滞后于 UI，停止输入 300ms 后收敛到最终值。

### 方案 B：只在 Dart 音量键入口防抖

代码较少，但 Slider、ReplayGain 和模式变化仍可与按键并发进入原生协调器，不能消除根因，因此不采用。

### 方案 C：增加 HID 超时或固定事务间隔

会让正常操作变慢，连续输入仍会不断触发事务，也无法保证只执行最终目标，因此不采用。

## 实现边界

修改保持在现有文件中：

- `UsbVolumeProtocol.kt`：增加可单测的待处理防抖剩余时间计算，并让同会话、同模式的待处理槽采用最新绝对目标。
- `UsbExclusiveAudioEngine.kt`：记录待处理目标更新时间，在取出待处理目标前按条件等待并重新检查。
- `UsbVolumeProtocolTest.kt`：覆盖快速连续输入、安静窗口重置、150ms 最小间隔、最终目标覆盖和 session 变化。

不修改 Flutter UI、用户文案、网络播放、ReplayGain 算法、HID 协议 ID、设备 quirk 或非 USB 页面。

## 安全与错误处理

- 防抖只减少写入，不绕过每次硬件写入后的 ACK 和寄存器读回验证。
- 安静窗口内只更新内存中的绝对目标，不向设备发送额外命令。
- 最新目标仍来自现有 Dart 音量步进和输出增益保护；本改动不生成额外的音量增加。
- 如果最终目标写入后仍发生真实 reader 失联，继续使用现有一次重启和有界恢复策略。
- 真机验证仍由用户先把音量降到安全范围并手动播放、按键；助手只安装和监听，不发送播放或音量命令。

## 验证标准

- 单元测试证明连续输入只保留最后目标，且新输入会延长 300ms 安静窗口。
- 单次空闲点击不增加 300ms 延迟。
- 快速连续点击期间最多执行首个目标和停止输入后的最终目标，不按点击次数形成事务序列。
- Android 相关测试、完整原生单元测试、Flutter USB 测试、`flutter analyze` 和 arm64 Profile 构建通过。
- 真机快速连续点击时不出现 reader 重启、同步冻结或突然增大；系统音量面板保持不显示。
